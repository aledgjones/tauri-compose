## Epic Summary

Epic 2 delivered the editing foundation for MVP tuplets. The team completed five story slices covering tuplet targeting, pitch-edit parity, slot add/remove behavior, drag-and-resize editing, and explicit delete/slice semantics.

The strongest outcome is that sequencer editing now handles tuplets through a stronger underlying model rather than through local exceptions. The epic preserved backend-owned truth, ownership-by-start, one-stored-event-per-tone rules, and `ui.flow_id` authority while improving the sequencer architecture enough to support more demanding editing behavior.

## What Went Well

- The team ended Epic 2 in a genuinely stronger architectural position. Tuplet editing is not a patchwork feature layered on top of the old sequencer model.
- The major rethink in Story 2.4 was ultimately the correct move. Replacing host-grid exception logic with the sequencer address lattice created a better foundation for move, resize, slice, and ownership-transfer behavior.
- Shared editing seams held up well across the epic. Tuplet-owned tones continued to mutate through existing action and backend paths instead of growing a parallel tuplet-only edit system.
- Backend-owned truth and ownership-by-start remained intact even as editing behavior became more complex.
- Validation discipline remained strong. Story records consistently cite focused frontend and Rust regressions plus repo-level lint, typecheck, test, and clippy coverage.
- Epic 1 follow-through was real in several places: the targeting contract was tightened before implementation, scope notes were sharper, and architectural guardrails were treated as fixed constraints rather than optional guidance.

## Challenges And Friction

### 1. Story 2.4 stayed on the wrong model too long

The biggest delivery problem in Epic 2 was not that Story 2.4 was hard. The bigger problem was that implementation stayed too long with a flawed abstraction that had been designed for a simpler sequencer layout. The work accumulated special cases, translation logic, and workaround behavior before the rethink was forced through a separate change document.

The key failure was not only choosing the wrong first path. The deeper failure was not recognizing early enough that the growing workaround load was itself evidence that the abstraction was wrong.

### 2. The agent did not stop early enough when the abstraction started to fail

Epic 2 exposed a process gap: when implementation begins preserving a concept through multiple special cases, repair branches, or conversion layers, the agent needs to treat that as a code smell and ask whether the model itself should be reconsidered.

The team wants an earlier bailout and clarification pattern instead of continued work on a decaying approach. A hard problem is acceptable. Prolonged workaround accumulation without challenge is not.

### 3. Review calibration still generated noise

Review friction remains lower than the implementation issue above, but it is still material.

The least useful review pressure came from requests for defensive error handling around states that may be theoretically imaginable but not actually reachable through the real UI and state model. That kind of coding pressure adds code and structural complexity without increasing product quality.

The right standard is not to dismiss those concerns blindly. The right standard is to verify reachability through actual UI flows and state transitions. If a path is real, it is a bug or a valid error boundary. If it is not reachable, forcing defensive scaffolding around it is usually negative value.

Future-work findings were less harmful, even when they were already planned, because they can still reveal story gaps. They still need correct classification so already-owned follow-up work is not misreported as a current-story defect.

### 4. BMAD artifact growth is now affecting iteration quality

Artifact size and repetition are consuming too much context budget. That is no longer just a documentation-style complaint. It is now affecting practical iteration by leaving less room for active problem-solving before the conversation has to compact.

This is a process problem in its own right and should be addressed separately from the Epic 2 retro close.

## Key Learnings

- The biggest win in Epic 2 was not a single feature. It was replacing a weak sequencer abstraction with a stronger one that can support tuplet editing coherently.
- A growing pile of special cases, workaround branches, or translation logic is a code smell, not proof that the current implementation path deserves more persistence.
- The agent should pause when it is struggling to preserve an invariant through increasingly indirect logic and should ask whether the underlying abstraction is wrong.
- Review value drops when it pressures the codebase to handle theoretically possible but practically unreachable states. Reachability should be validated through real UI and state flows first.
- Future-work findings should still be surfaced, but they should be classified as already-owned follow-up work when that is the truth.
- Process artifacts can become a product-delivery problem when they consume too much context to iterate effectively.

## Significant Discoveries

The most important discovery of Epic 2 is that tuplets are not a minor extension of the original sequencer assumptions. They require a stronger editing model. Once the team accepted that and reworked the abstraction, the implementation path became much more coherent.

The secondary discovery is process-related: implementation waste from staying with the wrong abstraction is more expensive than review noise or documentation overhead, even though those are still worth fixing.

## Final Assessment

Epic 2 is complete and successful. It shipped the expected tuplet-editing behaviors and materially improved the sequencer architecture at the same time.

The biggest lesson is not that complex stories need more persistence. The bigger lesson is that complex stories need earlier recognition of abstraction failure. Epic 3 should build on Epic 2's stronger editing foundation while applying a firmer stop-and-rethink rule whenever workaround-heavy logic starts to accumulate.
