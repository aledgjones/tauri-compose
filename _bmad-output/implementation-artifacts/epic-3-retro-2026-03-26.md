## Epic Review

### What Went Well

- Epic 3 stayed disciplined about compact score-context ownership. The team kept route visibility, route changes, recovery signaling, and same-session stability on the existing Sequence seams instead of growing new routing or repair surfaces.
- Backend truth held through the epic. Route readiness, route validity, and plugin-session state stayed Rust-owned, and the frontend work remained presentation and command wiring rather than a second route-state model.
- The epic handled validation-first stories well. Three of the four stories were essentially prove-and-tighten slices, and the work stayed bounded instead of inventing activity to make the stories look larger than they were.
- Regression coverage improved in the right places. The row, select, rack panel, and a targeted runtime-activation seam all gained checks that now protect the compact rack-first route model.
- Same-session stability got a concrete improvement without architectural churn. The rack panel now preserves backend-assigned plugin truth even when the assigned plugin is no longer selectable or disappears from inventory during the session.

### What Was Hard

- Epic 3 was another brownfield reconciliation epic. The repo already had meaningful routing behavior, so the main challenge was separating true defects from proof-oriented churn and writing story artifacts that matched reality.
- Vocabulary still needed active discipline. Inventory availability, routing usability, route readiness, and plugin-session stability are different concepts, and several story notes had to reinforce those boundaries repeatedly.
- Sprint bookkeeping drift persisted longer than it should have. All Epic 3 stories were done while the epic-level status still said `in-progress` and the retrospective entry still said `optional`.
- Validation posture was honest but not perfectly clean. Story 3.3 hit unrelated repo-wide clippy warnings, which did not invalidate the seam-local work but did show that the backend quality baseline is still noisy.
- The biggest execution risk was reopening stable seams through unnecessary UX changes. The team had to keep choosing the smallest safe correction over the more tempting “better workflow” rewrite.

## Key Lessons Learned

1. Validation-heavy brownfield stories need just as much rigor as feature stories. “Mostly already there” is exactly when teams overclaim, drift scope, or miss subtle state-contract bugs.
2. Compact score-context UX works when the backend contract is strong. Epic 3 proved that clarity came from tightening state truth and option shaping, not from adding more controls.
3. Missing or unavailable inventory must not erase backend-assigned route or plugin truth. Preserving that truth in the UI is part of stability, not cosmetic polish.
4. Explicit unrouted normalization is a feature, not a downgrade. It keeps recovery honest and avoids frontend-only interpretations of degraded route state.
5. Sprint tracking must close at the same time as the retro. If epic-level status lags story completion, planning signals become unreliable exactly when the next work decision matters most.

## Significant Discoveries

- The supported MVP route-authoring workflow is still the existing bounded dropdown. Epic 3 did not uncover evidence that a richer route picker is needed yet.
- Same-session stability issues can surface first as presentation-contract failures, not only as runtime crashes. The missing-plugin display bug in Story 3.4 is the clearest example.
- The compact row-state model is now stronger because it maps multiple backend states into one bounded user-facing recovery signal without inventing extra UI.
- The planning confusion came from overlapping plan generations: the original forward sequence was abandoned, then the team course-corrected into the stabilization path that ultimately landed across Stories 1.3 through 1.6 and Epics 2 and 3. With that work complete, Epic 4 is now the correct next sequence step.
