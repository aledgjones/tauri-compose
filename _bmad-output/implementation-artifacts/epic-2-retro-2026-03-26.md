## Epic Review

### What Went Well

- Epic 2 stayed disciplined about brownfield reality. The team repeatedly audited existing seams first and refined them instead of rebuilding plugin inventory, picker, or editor-host paths from scratch.
- Backend ownership boundaries held. Plugin inventory remained machine-local and Rust-owned, Plugin Manager stayed app-scoped, and Sequence score-context surfaces stayed focused on the current musical task.
- Review feedback was incorporated productively rather than defensively. The clearest example was the distinction between inventory visibility and score-context selectability: blocked plugins stayed visible in Plugin Manager for registry health, while they were removed from score-context assignment choices.
- The epic preserved the rack-first model while tightening user-facing language. Score-context plugin selection became more compact and musician-friendly without collapsing into host-topology UI.
- Story 2.4 closed responsibly against the actual codebase rather than forcing cosmetic changes just to literalize acceptance criteria. That was the right scope decision.

### What Was Hard

- Several stories were reconciliation and hardening stories, not greenfield implementation stories. That made documentation drift and overclaim risk higher than usual because the repo was already ahead of the current sprint ordering in some areas.
- The distinction between three concepts needed repeated clarification across the epic: inventory availability, routing usability, and bounded native-editor support. Without that distinction, UI and docs drifted quickly.
- Validation flow was temporarily blocked by unrelated stale expectations in the repo-wide JS suite during Story 2.1. Even though the blocker was outside the story’s core feature, it still affected story closure.
- Scope creep pressure kept showing up around plugin UI. The team had to keep rejecting proof-oriented surfaces that would have widened Plugin Manager or the editor-host workflow beyond the intended product model.

### Continuity Insights

- Epic 1’s biggest lesson did carry forward where it mattered most: the stories were written against the corrected ownership model rather than the earlier ambiguous one.
- The team applied the app-scoped versus score-context separation consistently through all four stories, which reduced the risk of a second frontend-owned inventory model appearing.

## Key Lessons Learned

1. Brownfield-first story execution works when the repo is ahead of the plan. Audit first, then narrow the gap. Do not rebuild for the sake of visible activity.
2. Inventory visibility, routing usability, and editor-host support are different truths and must stay separate in both code and documentation.
3. App-scoped windows and score-context panels are now a proven product boundary, not a tentative preference. Epic 3 should treat that split as fixed.
4. Story records need one more round of discipline when draft code changes are discarded. The final artifact must describe the final codebase, not the most interesting path explored during implementation.
5. Repo-wide validation noise can still shape delivery. When unrelated failing expectations block closure, the team needs to treat the baseline honestly and either fix it or explicitly waive it.

## Significant Discoveries

- The repo was already materially ahead of the sprint ordering for Epic 2, so the real work was contract tightening, test hardening, and documentation correction rather than large feature delivery.
- Plugin Manager’s strongest product value is as the canonical app-scoped registry and health surface. It becomes weaker, not stronger, when it starts to absorb score-context routing or editor-launch responsibilities.
- The Sequence rack surfaces can stay compact without losing clarity if they consume backend-owned truth and resist explanatory sprawl.
- Story 2.4 confirmed that the bounded native-editor handoff can remain a deliberately secondary seam without becoming a broader plugin-host workflow.
