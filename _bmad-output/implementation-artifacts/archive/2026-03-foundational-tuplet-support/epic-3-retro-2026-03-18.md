## Epic Summary

Epic 3 delivered the notation-facing half of foundational tuplet support. The team completed four story slices covering parser-owned tuplet notation derivation, native bracket and number rendering, coherent rendering of notes, rests, ties, and beams, and final spacing/layout integration inside the existing score surface.

The strongest outcome is continuity. Epic 3 did not fragment into separate parser, renderer, and layout interpretations of tuplets. The work stayed anchored to one backend-owned model, one boundary/projection contract, and one native score pipeline.

## What Went Well

- The team preserved a clean story chain across 3.1 through 3.4. Each story consumed the prior contract instead of rebuilding tuplet logic in a parallel path.
- Backend-owned truth held. Parser, draw, hit-test, and spacing changes stayed in Rust and avoided frontend reconstruction shortcuts.
- Scope control improved materially versus Epic 2. The story records consistently reinforced what each story did not own, which reduced architecture drift.
- Validation remained strong. Story records cite focused Rust regressions plus repo-level `cargo test`, `cargo clippy`, `npm run lint`, and `npm run check-types` runs.
- Review follow-through was effective. The 3.1 record shows substantive issues were fixed at the root contract level rather than patched at the symptom level.
- Spacing discipline held in 3.4. Tuplets were integrated into the existing widest-needed spacing model without introducing a tuplet-only slot family.

## Challenges And Friction

### 1. Boundary and projection semantics remain easy to regress

The main technical friction in Epic 3 was not uncertainty about the target model. It was how easy it remained to miss one boundary case while implementing that model. Story 3.1 needed follow-up fixes for tuplet-owned-to-host projection, explicit barline-driven splits, adjacent-tuplet carried tones, and persisted grouping handling.

The lesson is that the contract is now coherent, but still sharp-edged. Small deviations in one parser seam can create visible notation mistakes downstream.

### 2. Cross-story contracts required constant discipline

Epic 3 succeeded because the team repeatedly refused to let later stories “help themselves” to earlier-story responsibilities. That discipline was a strength, but it also created constant pressure. Every story needed to resist solving adjacent concerns by convenience.

That is acceptable friction. It is the cost of preventing duplicate models.

### 3. Documentation review remained high-frequency, low-change work

Each story correctly reviewed documentation impact, but 3.2 through 3.4 all concluded that no durable docs update was required. That is not wrong, but it is a signal that the team is paying repeated coordination cost to re-prove an unchanged answer.

The process should keep the review step, but the team should look for a lighter way to record repeated no-change outcomes when a story is explicitly implementing an already-documented contract.

## Key Learnings

- The parser-owned tuplet contract is now strong enough to support renderer, tie, beam, rest, and spacing work without a second interpretation layer.
- Boundary-aware musical logic must stay centralized. Projection mistakes in parser seams propagate into rendering and would later propagate into playback if not caught early.
- Story scope notes are doing real architectural work in this codebase. They are not bureaucracy; they are preventing parallel systems.
- The existing score pipeline was extensible enough to absorb tuplets without a renderer rewrite, provided the team stayed disciplined about consuming established contracts.
- Review quality is highest when it challenges real contract gaps and regressions rather than hypothetical defensive scaffolding.

## Evidence From The Epic

- Story 3.1 established anchored local tuplet notation tracks, kept semantic address distinct from written duration and host occupancy, and fixed the important carry-forward projection regressions before closing.
- Story 3.2 rendered tuplet brackets and numbers natively from parser-owned metadata and added native tuplet hit targets without overlay reconstruction.
- Story 3.3 made notes, rests, ties, and beams consume the isolated tuplet unit coherently, including cross-context tie continuity.
- Story 3.4 integrated tuplets into the shared horizontal spacing model, comparing ambient host width against local tuplet demand and reusing existing slot patterns only.

## Next Epic Preview

Epic 4 focuses on playback. It depends directly on Epic 3 leaving notation projection and boundary semantics stable, because playback now needs to consume the same exact backend-owned timing model instead of inventing a transport-only interpretation.

### Dependencies Already Satisfied

- Tuplet-local semantic structure is now explicit and backend-owned.
- Boundary splitting and continuity rules are clearer than they were at the end of Epic 2.
- Renderer and spacing now consume isolated tuplet units instead of flattening them into host-only assumptions.
- Hit targets and selection behavior already align with the native tuplet model.

### Preparation Needed For Epic 4

- Start playback work from the same carry-forward invariants used in parsing and rendering, especially ownership-by-start and boundary-derived continuity.
- Treat Story 4.1 as a contract story, not just an implementation story. Playback projection must be defined as carefully as parser projection was.
- Add focused playback regressions early for mixed tuplet and non-tuplet passages so transport ordering mistakes are caught before they spread.
- Preserve the current no-parallel-model discipline. There must not be a playback-only tuplet timing interpretation.

Epic 4 should keep that same discipline and apply it to playback before transport-specific assumptions start to drift away from the now-established notation and persistence model.
