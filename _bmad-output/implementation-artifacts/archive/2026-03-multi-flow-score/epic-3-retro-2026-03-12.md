## Overall Outcome

Epic 3 is accepted as complete and ready to hand off into Epic 4. The epic delivered the intended foundation for trustworthy multi-flow rendering by sequencing observability, notation safety, recalculation isolation, visual stability, and performance characterization in a deliberate order.

The strongest outcome is not just that all five stories were completed, but that the epic replaced intuition with evidence. The team now has explicit render-scope diagnostics, meaningful regression protection, flow-scoped recalculation behavior, and a measured single-flow baseline that can anchor future work.

## What Went Well

- The epic stayed architecture-first and sequence-disciplined: observability, then safety, then isolation, then stability, then validation.
- The team kept Rust as the source of truth and extended existing seams instead of introducing parallel frontend-owned models.
- Performance visibility is now in a good place for ongoing work. The sampling workflow provides a credible baseline, and the debugger view gives maintainers a useful picture of what rendered and why.
- Verification remained part of delivery instead of cleanup at the end. Story work was tested as it progressed rather than being deferred.
- Epic 2 lessons were applied well: the team repeatedly tightened failing seams rather than redesigning broad systems.

## Challenges And Friction

### 1. Duplicate concepts instead of widened abstractions

The clearest avoidable friction was bolting new capabilities beside existing logic rather than widening the original abstraction to cover the broader case.

The example called out directly in the retro was `emit_affected_flow` versus `emit_affected_flows`. A single-flow case is not a distinct architectural concept; it is the one-item case of a multi-flow recalculation scope. Treating that as a separate concept increased API surface, increased review cleanup, and made the mental model less coherent than it needed to be.

### 2. Repeated review simplification

The team often had to ask for simplification and containment after the first implementation pass. That did not indicate instability in the core direction, but it did show a recurring tendency to let the first version land broader than necessary before being tightened.

### 3. Debugger value with presentation refinement still needed

The debugger view was considered excellent work and immediately useful, but it was also recognized as a strong start rather than a final form. The underlying truthfulness of the diagnostics is valuable; the remaining opportunity is presentation simplification without weakening that truth.

## Key Learnings

- Extend existing pathways before adding side-by-side variants. A one-item case is not a separate abstraction unless proven otherwise.
- Ask context-first questions before implementation begins: what already exists, what pattern already fits, and what should be widened rather than duplicated.
- Treat the renderer and update model like a small game engine. The relevant mental model is not ordinary app glue code; it is engine-style work with invalidation boundaries, cache reuse, partial updates, frame cost sensitivity, and truthful diagnostics.
- Performance visibility is now strong enough to support ongoing work rather than one-off story closure. That changes how future regression discussions should be conducted.
- Claims about preserved behavior need explicit evidence. The team performed best when it validated rather than inferred.

## Epic 4 Preparation

Epic 4 can proceed.

The retro identified the following preparation principles before implementation begins:

1. Start every story with a context-and-pattern audit.
2. State explicitly what existing seam, abstraction, or pathway the story extends.
3. Prefer generalizing the current path over introducing a second concept for the one-item case.
4. Use a game-engine mental model for rendering, invalidation, cache reuse, and contained updates.
5. Define lifecycle boundaries up front: source state, derived render state, cacheable artifacts, and invalidation triggers.
6. Tie tests to the existing seam so the extension is proven through the current system rather than a bolt-on path.

### Epic 4 Dependency Read

Epic 4 depends on Epic 3 leaving the multi-flow renderer observable, truthful, stable, and architecturally coherent. It also depends on `ui.flow_id` remaining the one authoritative active-flow slot while playback and desktop workflow behavior continue to preserve single-active-flow semantics where intended.

### Explicit Preparation Needs

- Define representative open, save, and reopen scenarios for multi-flow documents.
- Define playback validation scenarios where multiple flows are visible but playback remains scoped to the active flow.
- Keep persistence impact under active review so `.soloc` semantics do not drift accidentally.
- Preserve the Epic 3 evidence standard for any claim that behavior is preserved.
