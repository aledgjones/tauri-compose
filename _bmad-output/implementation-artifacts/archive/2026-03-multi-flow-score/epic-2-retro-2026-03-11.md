## Overall Outcome

Epic 2 is accepted as complete and ready to hand off into Epic 3. The epic delivered interaction confidence on top of the shared multi-flow surface established in Epic 1, and it did so mostly through verification, targeted hardening, and careful scope control rather than large new implementation layers.

This was intentionally a development-light epic. That is a positive outcome, not a sign of weak scope. Epic 1 carried much of the structural cost, and Epic 2 proved that foundation could support trustworthy hit-testing, selection, popovers, and active-flow coherence without forcing a redesign.

## What Went Well

- Validation and verification were real deliverables throughout the epic rather than after-the-fact checks.
- Epic 1 groundwork paid off as intended, reducing the need for broad new implementation work.
- The team repeatedly tightened existing contracts instead of introducing parallel systems.
- Rust and JavaScript ownership boundaries became much clearer, especially around selection handling and selection clearing.
- The strongest solutions came from proving the current contract first and only fixing the specific seam that failed.
- The epic maintained strong regression discipline around boundary hits, later-flow behavior, popover anchoring, and active-flow coherence.

## Challenges And Friction

### 1. Speculative complexity

The biggest source of drag was speculative complexity. Several implementation paths gave too much weight to hypothetical edge cases or impossible states, which made the code harder to reason about than the real system required.

This had two direct costs:

- code review became harder for the human reviewer because defensive logic had to be mentally untangled before the real behavior was clear
- bug fixing would have become slower because unnecessary branches obscure which states are credible and which are defensive fiction

### 2. Abandoned ideas lingering in implementation

The spec continued to pull implementation toward ideas that were no longer product direction, including flow-highlighting-related behavior. One story was ultimately removed, which is strong evidence that the planning artifacts and implementation path were not always aligned.

The key lesson is not just to update planning artifacts, but to prune invalidated ideas aggressively once the product decision is clear.

### 3. Popover overbuilding before simplification

The popover story was the clearest example of over-solving. It initially drifted toward a broader synchronization and lifecycle model, but the final outcome simplified substantially and reverted most of that complexity.

That was a useful signal: when the underlying contract is already sound, adding generalized coordination logic can be worse than keeping the seam narrow and event-local.

## Key Learnings

- Verification-first delivery works best when it starts by proving the current contract, not by designing for hypothetical failure modes.
- Speculative complexity is a real quality problem because it harms reviewability and maintainability even when the code still passes tests.
- The team should prefer deleting unnecessary complexity over preserving it out of caution.
- Backend and frontend ownership boundaries are much clearer now, especially around selection truth, explicit invalidation, and selection clearing.
- When the architecture is already sound, the right move is often to tighten the failing seam rather than introduce a more complete-looking system.

## Epic 3 Preparation

Epic 3 can start immediately.

The team aligned on the following architectural framing before new work begins:

- raw data model is the durable musical source of truth
- parsing into notation is the correctness-sensitive derived layer and should remain isolated by flow whenever dependencies allow
- render instructions are downstream presentation artifacts and should remain lightweight and cache-friendly

### Critical Preparation Before Story Work Starts

1. Re-state the architecture boundary at the top of the epic: raw data model, per-flow notation parsing, downstream render instructions.
2. Treat observability as the first implementation concern so affected-flow versus wider recalculation work is visible in diagnostics.
3. Keep parser isolation as the default assumption: changing one flow should not trigger whole-score notation recomputation unless a real dependency requires it.
4. Define success in evidence terms: tests and timing output must prove isolation, notation safety, and stability.
5. Add a standing review question for every Epic 3 story: which layer changed, and what proof shows the other layers stayed isolated?

### Parallel Preparation

- tighten notation-safety regression coverage before changing recalculation boundaries
- extend render-timing output so it distinguishes single-flow, multi-flow, and affected-flow recalculation work
- prepare representative validation scenarios for one-flow edits, other-flow edits, unchanged-flow rerenders, and larger multi-flow cases
- keep story wording sharp enough to avoid speculative work framed as generic edge-case handling

### Explicit Avoids

- do not optimize the render layer first just because it is visible
- do not blur parsing and rendering into one generalized recalculation model
- do not implement protections for impossible states without evidence they are reachable
- do not invent more complicated cross-flow invalidation behavior before diagnostics show it is necessary
