## What Went Well

## Main Failures

Epic 6 exposed several process and implementation-discipline failures that should now be formalized as repo rules.

### 1. Identity Discipline Drifted

- `UniqueId` belongs to score-owned entities only.
- External or app-scoped entities such as expression maps, rules, conditions, and actions should use UUIDs rather than score `UniqueId` values.
- This boundary was not held firmly enough early in the epic, and the resulting ambiguity contributed to unnecessary rework.

### 2. Nested Array Data Lacked Mandatory Identity

- Any entity persisted in a `Vec` or array must have a stable id.
- The expression-map workflow initially tolerated index-driven mutation and wide replacement updates, which made rendering, lookup, reorder, and targeted mutation harder than necessary.
- This led directly to fragile React keys, index-coupled selection logic, and overcomplicated update code.

### 3. Frontend API Boundaries Drifted Too Wide

- JavaScript should not own durable data or invent canonical ids for backend-owned entities.
- The healthier pattern is a larger set of tight, explicit actions that delegate ownership to Rust, not broad `upsert` actions where JavaScript constructs or reshapes backend truth.
- Epic 6 improved once targeted Rust commands replaced broad nested-map upserts.

### 4. Tauri Command Placement Became Too Centralized

- `src-tauri/src/lib.rs` absorbed too many command handlers.
- Tauri commands should live close to the domain they control, with `lib.rs` reserved for true app-wide setup and wiring.
- The expression-map work made that structural smell more obvious.

### 5. New Features Repeatedly Tried To Carry Legacy Compatibility They Did Not Need

- Expression maps were a new feature, but implementation repeatedly drifted toward compatibility handling that was not required.
- This created unnecessary complexity and had to be corrected multiple times.
- The repo needs a firmer rule: do not add compatibility residue for development-only or not-yet-shipped new features unless a concrete migration or released-user need exists.

### 6. Optimistic Updates Were Used Without Justification

- The JavaScript to Rust bridge is fast enough that backend-owned state should be treated as the default source of truth in almost all cases.
- Epic 6 briefly accumulated optimistic local state and wide local drafts that made the editor harder to reason about.
- Deterministic local update paths should require an explicit, strong justification rather than being assumed as a general frontend pattern.

### 7. Story 6.3 Was Too Large And Too Broad

- Story 6.3 combined substantial workflow UI, nested data editing, drag reorder semantics, authoring semantics, and ownership cleanup into one story.
- That made review chunking necessary and encouraged MVP scope drift before the final scope was cut back.
- The result shipped, but the path there was noisier than it needed to be.

## What Was Hard

- The hard part of Epic 6 was not the product concept. The hard part was keeping identity, mutation, and ownership rules tight while building a nested authoring workflow.
- Drag-and-drop complexity in Story 6.3 turned out not to be only a drag problem. It was a combined identity, selection, and mutation-ownership problem.
- The expression-map model works well for note-local semantics today, but future score-linked semantics such as persistent playing techniques remain an open modeling question.
- Intermittent plugin UI hangs remain an unresolved operational risk even though they were not an Epic 6 acceptance-criteria failure.

## Key Lessons Learned

1. `UniqueId` is for score-owned entities only. App-scoped or external entities must use UUIDs.
2. Any persisted or mutable entity that lives in a `Vec` or array must have a stable id.
3. JavaScript APIs should delegate to Rust-owned truth through tight, explicit commands instead of reconstructing backend state through wide upsert surfaces.
4. `src-tauri/src/lib.rs` should not become a catch-all command container; commands belong near their owning domain.
5. New features should not accumulate compatibility residue without a concrete released-user need or migration requirement.
6. Optimistic updates are not a default pattern in this app; backend echo should win in almost all cases.
7. Stories that combine nested data modeling, workflow UI, and interaction-heavy editing need stricter MVP slicing before implementation starts.

## Significant Discoveries

- The most important Epic 6 discovery was not musical. It was architectural discipline around identity and mutation ownership.
- Stable ids for nested reusable-asset entities are not just a React rendering convenience. They are a core correctness requirement for lookup, mutation, reorder, and selection.
- A broader API surface with narrow task-specific backend commands is easier to reason about in this codebase than a smaller surface of generic upsert endpoints.

## Open Questions And Risks

### Open Questions

1. Expression maps currently work well for individual tones, but the long-lived playing-technique model is still unresolved. A technique such as pizzicato behaves more like a persistent score flag that is later cancelled by arco than a property that lives only on one tone.
2. The correct future home for those persistent technique semantics is not yet defined. The team should decide whether that belongs in the shared score semantic model, an expanded expression condition model, or a separate owned seam that expression maps can consume.

### Risks

1. Intermittent plugin UI hangs remain present when opening the plugin UI. The issue is not constant, but it is credible enough to carry forward as a product and technical risk.
2. If future reusable-asset workflows do not start with strict identity and command-boundary rules, the same mutation and optimistic-state churn could recur.

## Closing Note

Epic 6 succeeded on product outcome and architectural direction. The work proved that bounded expression-map realism can live on the existing backend-owned playback path without bloating the score-context UI or collapsing project and app-scoped ownership. The main lesson is narrower and more operational: the team needs explicit non-negotiable rules for id taxonomy, stable identity in arrays, backend-owned mutation seams, and when optimistic state is forbidden. Those were the real sources of churn. If those rules are formalized now, Epic 6 becomes a useful inflection point rather than a warning that repeats.
