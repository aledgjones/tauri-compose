## Epic Review

### What Went Well

- Epic 1 ended in a materially stronger place than it began. The final model for plugin ownership, readiness, editor attach or detach, and reopen behavior is substantially clearer and more trustworthy.
- The mid-epic correction that introduced Stories 1.5 and 1.6 was the right call. It exposed and then closed a real ownership gap instead of letting an implicit assumption survive into later epics.
- Once slot ownership was refined from a generic "slot references plugin" model to a concrete "slot owns a live plugin instance" model, several previously confusing bugs and hang investigations became easier to reason about and fix.
- The team did not just patch symptoms. It rooted out flawed model interpretation and improved the architecture underneath the behavior.
- Prior-art research from established open-source VST hosts was one of the strongest positive forces in the epic. Proven patterns around host lifecycle, instance ownership, restore behavior, and editor targeting gave the team a much better frame for implementation and debugging.
- The broader epic rewrite and course correction helped restore confidence after earlier planning drift. The roadmap moved back toward a more defensible foundation instead of continuing on top of a weak interpretation.

### What Was Hard

- The generated planning and documentation set was too dense to fully validate by assumption. Important ownership semantics were present in the material but not explicit enough to prevent misinterpretation.
- A critical domain assumption felt "obvious" to the project lead and therefore remained implicit: a slot houses a specific plugin instance, not a plugin only in a generic sense.
- That implicit assumption allowed the implementation path to drift into a flawed model interpretation before the problem became undeniable.
- The earlier plan abandonment was disconcerting and created understandable concern about whether the work would stabilize in time.
- The corrective stories landed mid-epic, which increased coordination pressure even though it was the right decision.

## Key Lessons Learned

1. Domain model truths must be stated explicitly at the ownership boundary, especially for runtime lifecycle, persistence, and recovery work.
2. Prior art should be used early to pressure-test domain model interpretation for mature third-party integration domains like VST hosting.
3. If Compose intentionally deviates from known-good host patterns, that deviation should be named and justified explicitly rather than discovered later through bugs.
4. Compose should preserve its own UX ergonomics, but it should not reinvent known technical integration patterns for third-party systems.
5. When behavior appears unstable or mysterious, challenge the model interpretation early instead of only debugging isolated symptoms.
6. Epic 2 looking lighter is a positive outcome of Epic 1's correction, but that should be confirmed by a targeted sanity check rather than assumed.

## Significant Discoveries

- The core issue was not random instability. The system was often behaving consistently against the wrong ownership model.
- Hangs and lifecycle bugs became substantially easier to investigate once the slot-owned-instance model was made explicit.
- Open-source VST host research is not optional background reading for this work; it is a practical engineering input that should shape architecture-sensitive stories.
- The corrected Epic 1 model now provides a much stronger base for plugin-management and inventory-facing work in Epic 2.
