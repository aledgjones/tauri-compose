## Epic Summary

Epic 1 delivered the full persistence and authoring foundation for MVP triplet support. The team shipped eight completed story slices covering the persisted tuplet container model, popover creation, sequencer-region rendering, the non-nestable MVP constraint, tuplet note entry, reconciliation over existing material, deterministic `.soloc` round-tripping, and versioning/offline workflow protection.

The strongest architectural outcome is that tuplets now behave as backend-owned first-class score data rather than UI annotations. The epic kept the one-stored-event-per-tone rule intact, preserved ownership-by-start-position across host and tuplet contexts, and reused the existing file, action, and mutation seams instead of creating parallel systems.

## What Went Well

- The team kept Rust as the source of truth and avoided frontend-owned rhythmic state throughout the epic.
- The implementation stayed incremental. Each story extended existing seams instead of forcing a broad rewrite.
- Validation discipline was strong. Story records consistently captured lint, typecheck, Rust test, and clippy evidence, and the current workspace state shows those checks passing.
- The team corrected scope cleanly when needed. Story 1.3 was narrowed to the shipped sequencer contract, and Story 1.3A simplified child storage before more editing logic accumulated on the wrong model.
- Persistence decisions were disciplined. Tuplets round-trip through the existing `.soloc` path, and the team explicitly documented why no new migration was warranted for unreleased tuplet-bearing files.
- Documentation moved with the implementation in the areas that matter: data model, development guidance, architecture notes, and project rules.

## Challenges And Friction

### 1. Story bookkeeping drift

Several stories needed review-driven cleanup because the record of work lagged the actual implementation. File lists, migration claims, and story notes were occasionally out of sync with the code. The code quality held up, but the paper trail required avoidable correction.

### 2. Scope boundaries were not always sharp enough up front

The epic benefited from explicit scope notes, but some review findings still overreached into later-story or later-epic work. The important nuance is that this is not a reason to ignore bugs or missing requirements. Review still needs to surface complete-feature concerns. The rule is that those concerns must be cross-checked against planned future work before they are classified as defects in the current story. Several points raised during Epic 1 were excellent observations about complete functionality, but they were already intentionally owned by later stories because the feature was being delivered in manageable stepping stones.

### 3. UX and selection follow-through remains a live seam

Epic 1 delivered creation, visibility, and insertion, but some interaction polish is intentionally deferred. The most visible carry-forward is member targeting clarity: child-tone selection now works, but the bottom-bar summary and broader editing semantics still belong to Epic 2.

### 4. Review calibration improved during the epic, not before it

The review process clearly caught real issues, which is good. It also surfaced a process gap: findings need to be checked against the story's explicit scope and deferrals before they are classified as missing implementation. The right review standard is not "reject scope leakage and move on." The right standard is "surface the concern, then verify whether it is a current bug or requirement miss versus already-accounted-for future work."

### 5. Story 1.4 exposed both story ambiguity and implementation-quality problems

Story 1.4 had to be approached more than once before it reached the expected bar. That was not just one problem. The story left too much room for interpretation, especially around subjective implementation decisions and the desired shape of the API surface. At the same time, the first pass was not strong enough on engineering quality: it introduced parallel and duplicate API flows where the cleaner solution was to extend and refine the existing API seams.

## Key Learnings

- Preserve architecture through seam extension, not parallel APIs. Epic 1 was strongest when it extended the existing track-owned mutation and file-workflow contracts.
- Course correction is a strength when it happens early. Simplifying tuplet child content before deeper editing work prevented downstream defensive complexity.
- A precise story record matters. If the code, tests, and story artifact disagree, the team pays for it later in review.
- Review quality improves when scope discipline is explicit. Deferred work should be tracked as follow-on ownership, not reported as a defect in the wrong story, but reviewers still need to cross-reference future work so true bugs and missing requirements are not excused away.
- For stories with ambiguous or subjective implementation choices, the agent should ask about those decisions before starting. That is now a workflow rule, not an optional refinement tip.
- A story can fail twice: once because the story leaves too much unstated, and again because the implementation takes the more complex path instead of honing the existing seams. Story 1.4 did both.
- Epic 2 should start from the current backend-owned tuplet contract, not revisit foundational persistence decisions.
